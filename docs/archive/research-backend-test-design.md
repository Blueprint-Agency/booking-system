# Research: is the backend test suite's design sound?

**Date:** 2026-09-25 · **Primary sources only** (postgresql.org, nodejs.org, hono.dev, orm.drizzle.team, the postgres.js README, martinfowler.com, kentcdodds.com, Google Testing Blog, *Software Engineering at Google* at abseil.io, 12factor.net). Every claim carries its source URL. **UNSUPPORTED** means no primary source was found for it.

**Scope:** the *design* of the `be/` suite: real Postgres, RLS, in-process HTTP, fixtures and cleanup, config at module load, and the mix of test kinds. CI speed flags (isolation mode, fsync, sharding) are covered in `research-backend-ci-test-speed.md` and are left out here.

**What the repo does (from the code):** `be/src/test/harness.ts` migrates and seeds one scratch database per checkout, creates the `booking_app` role, and gives the app `DATABASE_APP_URL` as that role. The harness keeps the owner connection for fixtures (`be/src/test/environment.ts` `appRoleUrl`). Tests call the real Hono app with `app.request()` and sign in through Better Auth over HTTP. `withTenant` (`be/src/db/index.ts`) opens its own transaction on the app's pool and runs `set_config('app.tenant_id', …, true)`. Fixtures are removed by explicit `DELETE`s in `after` hooks (`be/src/test/member-fixtures.ts` `cleanup`). Config is read at import: `be/src/env.ts`, the `DATABASE_APP_URL` pool in `db/index.ts`, `R2_*` constants in `lib/r2.ts`, `PLATFORM_ADMINS` in `middleware/platform-admin.ts`. Stripe has a seam instead (`setStripeFactory` in `lib/stripe.ts`). There are 133 `*.test.ts` files; 72 call `startTestApp`.

## Verdict: is the design wrong in the first place?

**No. The core design is what the primary sources recommend.** Postgres documents that owners and superusers bypass RLS, so a real database reached as a non-owner role is the only way to test isolation ([PG RLS](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)). Google says "our first choice for tests is to use the real implementations" ([SWE@Google ch13](https://abseil.io/resources/swe-book/html/ch13.html)). Hono's docs use `app.request()` for testing ([Hono](https://hono.dev/docs/guides/testing)). Fowler calls the argument over test proportions "moot" ([Test Shapes](https://martinfowler.com/articles/2021-test-shapes.html)).

The weak spots are secondary:
1. **Config read at module load.** Fowler says "configuration of services is separated from their use" ([Injection](https://martinfowler.com/articles/injection.html)), and the Stripe seam already does this. The rest of the config does not.
2. **Cleanup after each test instead of rebuilding a known starting state.** Fowler prefers rebuilding ([Non-Determinism](https://martinfowler.com/articles/nonDeterminism.html)).
3. **A slow test in the gate that every change must pass.** Google's CI chapter keeps only "fast, reliable" tests in presubmit ([SWE@Google ch23](https://abseil.io/resources/swe-book/html/ch23.html)).

Per-test transaction rollback is the textbook fix for #2. It does not fit this app as-is, because the app opens its own transactions on its own pool as its own role (see claim 4).

## Evidence

### 1. RLS needs a real Postgres and a non-owner role
- "Superusers and roles with the `BYPASSRLS` attribute always bypass the row security system when accessing a table. Table owners normally bypass row security as well, though a table owner can choose to be subject to row security with ALTER TABLE ... FORCE ROW LEVEL SECURITY." ([PG RLS](https://www.postgresql.org/docs/current/ddl-rowsecurity.html))
- **Correction:** `FORCE` does not help against a superuser connection. The migration's `ENABLE` + `FORCE` (ADR 0002) covers the owner. It is the separate `booking_app` role (`NOSUPERUSER … NOBYPASSRLS`, `be/src/db/roles.ts`) that covers the superuser case. Both are needed, and the repo has both.
- "If no policy exists for the table, a default-deny policy is used" ([same page](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)). This is why a query with no Tenant context sees nothing, and why `inTenantContext` exists in the harness.
- Caveat for isolation tests: "Referential integrity checks, such as unique or primary key constraints and foreign key references, always bypass row security" ([same page](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)). A cross-tenant unique-constraint error can therefore leak a row's existence. That can only be tested against a real database.
- `set_config(…, true)`: "If `is_local` is `true`, the new value will only apply during the current transaction." ([PG admin functions](https://www.postgresql.org/docs/current/functions-admin.html)) This matches `withTenant`.

### 2. Real collaborators vs mocks
- Google: "our first choice for tests is to use the real implementations of the system under test's dependencies; that is, the same implementations that are used in production code." It also says "prefer realism over isolation." Where a fake is used, "the team that owns the real implementation should write and maintain a fake." ([SWE@Google ch13](https://abseil.io/resources/swe-book/html/ch13.html))
- Fowler: "The classical TDD style is to use real objects if possible and a double if it's awkward to use the real thing." ([Mocks Aren't Stubs](https://martinfowler.com/articles/mocksArentStubs.html)). The article gives no database-specific rule.
- Fowler's *narrow* integration tests use doubles for *separate services*, with contract tests to check the doubles ([IntegrationTest](https://martinfowler.com/bliki/IntegrationTest.html)). This fits Stripe, R2 and Resend (external services, doubled via `setStripeFactory` and the `NODE_ENV=test` mailer switch). It does not fit Postgres. Here the database is not a separate service: its RLS policies *are* the isolation logic under test.
- No primary source says "mocking the DB makes isolation tests pass vacuously" in those words. It follows from claim 1: a double has no policies to enforce. The repo's own comments make the same point (`environment.ts`, `db/index.ts`).

### 3. `app.request()`
- "All you need to do is create a Request and pass it to the Hono application to validate the Response. You can then use the useful `app.request` method." There is also a typed `testClient` helper. No server is started. ([Hono testing](https://hono.dev/docs/guides/testing))
- Fowler calls tests through an API below the UI "SubcutaneousTests" and names them as the pyramid's middle layer ([TestPyramid](https://martinfowler.com/bliki/TestPyramid.html)).

### 4. Transaction rollback, savepoints, template databases
- Fowler: "One trick that's handy when you're using databases, is to conduct your tests inside a transaction, and then to rollback the transaction at the end of the test." ([Non-Determinism](https://martinfowler.com/articles/nonDeterminism.html))
- **Why it doesn't fit as-is:** postgres.js: "Postgres.js will reserve a connection for the transaction and supply a scoped sql instance". "Connections are automatically taken out of the pool if you start a transaction using sql.begin()" ([postgres.js README](https://github.com/porsager/postgres)). `withTenant` calls `pool.transaction`, which puts it on a *different connection* from any test-side transaction. Rows the test wrote but did not commit are invisible to it, and nothing it writes can be rolled back by the test. A second `BEGIN` on the same connection does not nest either: "Issuing BEGIN when already inside a transaction block will provoke a warning message. The state of the transaction is not affected." ([PG BEGIN](https://www.postgresql.org/docs/current/sql-begin.html))
- **Documented building blocks for a workaround:**
  - Savepoints: "Savepoints can only be established when inside a transaction block" ([PG SAVEPOINT](https://www.postgresql.org/docs/current/sql-savepoint.html)).
  - Nested transactions become savepoints: "Drizzle ORM supports savepoints with nested transactions API" ([Drizzle](https://orm.drizzle.team/docs/transactions)).
  - One pinned connection: `sql.reserve()` "pulls out a connection from the pool, and returns a client that wraps the single connection" ([postgres.js README](https://github.com/porsager/postgres)).
  - The role: `SET LOCAL ROLE` limits a role change to the current transaction, after which "permissions checking … is carried out as though the named role were the one that had logged in originally" ([PG SET ROLE](https://www.postgresql.org/docs/current/sql-set-role.html)).
  - Putting these together: the owner opens an outer transaction on a reserved connection, runs `SET LOCAL ROLE booking_app`, and the app's `db` becomes a nested `tx.transaction` (a savepoint) on that connection. In principle `set_config(…, true)` and RLS then behave as in production, and the outer rollback wipes everything.
  - **Not verified:** no primary source documents this whole pattern. It also changes the thing under test: the real pool, connection reuse, and the transaction-local leak that `rls.test.ts` pins are no longer exercised. Better Auth writes through its own adapter and would also have to use the pinned connection (not checked in Better Auth docs). Tests of concurrency or `repeatable read` cannot run inside one outer transaction.
- **Template databases:** "By default, the new database will be created by cloning the standard system database template1. A different template can be specified by writing TEMPLATE name." Restriction: "no other sessions can be connected to the template database while it is being copied. CREATE DATABASE will fail if any other connection exists when it starts." The docs also say it "is not (yet) intended as a general-purpose 'COPY DATABASE' facility". `WAL_LOG` (the default) is "the most efficient strategy in cases where the template database is small"; `FILE_COPY` "forces … a checkpoint both before and after" ([PG CREATE DATABASE](https://www.postgresql.org/docs/current/sql-createdatabase.html)). So the pattern is: migrate and seed a template once, disconnect, then clone per worker or per file. Roles are cluster-wide, so `booking_app` carries over. The per-database `GRANT CONNECT` in `ensureAppRole` is database-scoped and would need re-running per clone (inferred from `roles.ts`, not from a doc quote).

### 5. Config at module load
- Twelve-Factor: "The twelve-factor app stores config in environment variables", and config is "everything that is likely to vary between deploys" ([12factor Config](https://12factor.net/config)). **The chapter says nothing about when config is read or how tests should handle it.** "Validate at import" is a repo choice, not a Twelve-Factor rule.
- Node: "When process-level test isolation is disabled … it is possible for tests to interact with each other … if a test relies on global state, it is possible for that state to be modified by a test originating from another file." ([Node test runner](https://nodejs.org/api/test.html)) This is why `docs/md/testing.md` bans top-level `process.env` writes and first-importer dependencies, and why `environment.ts` has to be preloaded.
- Fowler: "The important issue in all of this is to ensure that the configuration of services is separated from their use". Also: "if you can't easily stub services for testing, then this implies a serious problem with your design" ([Injection](https://martinfowler.com/articles/injection.html)). Fowler adds that DI and Service Locator are equally stub-friendly. `setStripeFactory` is the Service Locator-style seam he describes. `R2_*` constants and `PLATFORM_ADMINS` captured at import are the opposite.
- Fowler, same idea for time: "Always wrap the system clock" ([Non-Determinism](https://martinfowler.com/articles/nonDeterminism.html)). `lib/clock.ts` already follows this.

### 6. Non-determinism, cleanup, quarantine
- "Keep your tests isolated from each other, so that execution of one test will not affect any others." On rebuilding the starting state versus cleaning up after: "In general I prefer the former, as it's often easier - and in particular easier to find the source of a problem." ([Non-Determinism](https://martinfowler.com/articles/nonDeterminism.html))
- Red builds: with 10 flaky tests in 100, the suite "will often fail … once that discipline is lost, then a failure in the healthy deterministic tests will get ignored too." Quarantine: "Place any non-deterministic test in a quarantined area. (But fix quarantined tests quickly.)", with a cap such as "only allow 8 tests in quarantine" (same source).
- Google: tests should be hermetic, containing "all of the information necessary to set up, execute, and tear down its environment". Also: "as you approach 1% flakiness, the tests begin to lose value" ([SWE@Google ch11](https://abseil.io/resources/swe-book/html/ch11.html)).
- **Repo:** cleanup runs in `after` hooks (e.g. `admin-catalogue.test.ts`, `customers-directory.test.ts`). A crashed or killed run leaves rows behind for the next run. Unique name prefixes and per-domain emails (`member-fixtures.ts`) reduce collisions but do not remove them. The two seeded tenants are shared by every file, so a file that changes tenant-wide settings (e.g. `marketingWas` in `admin-catalogue.test.ts`) is shared state. Fowler's rule points to starting from a known state, such as a fresh template clone, rather than trusting teardown. CI failing on skipped tests (`CLAUDE.md`) conflicts with quarantine as Fowler describes it. A quarantine would have to be an explicit, capped list.

### 7. Test proportion
- Fowler's pyramid: "many more low-level UnitTests than high level BroadStackTests running through a GUI". The problem it targets is UI tests being "brittle, expensive to write, and time consuming to run". He also says the pyramid-versus-alternatives difference "is probably illusory due to different definitions of 'unit test'" ([TestPyramid](https://martinfowler.com/bliki/TestPyramid.html)).
- Fowler's Test Shapes: the pyramid-versus-honeycomb argument is moot because of those differing definitions. He quotes Justin Searls: "Nearly zero teams write expressive tests that establish clear boundaries, run quickly & reliably, and only fail for useful reasons." ([Test Shapes](https://martinfowler.com/articles/2021-test-shapes.html))
- Dodds: "Write tests. Not too many. Mostly integration." Also: "The more your tests resemble the way your software is used, the more confidence they can give you." ([Testing Trophy](https://kentcdodds.com/blog/the-testing-trophy-and-testing-classifications))
- Google suggests 70/20/10 ([Just Say No to More E2E Tests](https://testing.googleblog.com/2015/04/just-say-no-to-more-end-to-end-tests.html)) and targets 80/15/5 ([SWE@Google ch11](https://abseil.io/resources/swe-book/html/ch11.html)). In Google's terms these integration tests are *medium* tests: localhost network, one machine.
- **Verdict:** defensible. Tenant isolation lives in RLS policies and middleware, and only an integration test exercises it. Dodds and Fowler (via subcutaneous tests and Test Shapes) support that. Google's mix is the one source that leans the other way. It applies at Google's scale, and its rationale is speed and failure isolation, not a claim that integration tests are wrong. Pure rules (finance ledger, time windows, parsing) should stay unit-tested.

### 8. Slow tests in presubmit
- "Only fast, reliable ones" belong in presubmit. Tests with "longer times and some instability" can run post-submit. "Most teams at Google run their small tests (like unit tests) on presubmit." And: "waiting a long time to run every test during code submission can be severely disruptive" ([SWE@Google ch23](https://abseil.io/resources/swe-book/html/ch23.html)).
- A 66-second load-style test on every PR runs against this guidance. It fits a post-merge or nightly job, provided failures there are acted on. **Repo note:** the 66 s figure came from the brief; this research did not identify which file it is.

## What the sources say to change, in priority order

1. **Keep the core:** real Postgres, the `booking_app` non-owner role, two tenants, `app.request()`. Every source above supports it. Doubles stay for external services only (Stripe, R2, Resend), per [Fowler IntegrationTest](https://martinfowler.com/bliki/IntegrationTest.html) and [SWE@Google ch13](https://abseil.io/resources/swe-book/html/ch13.html).
2. **Separate config from its use.** Replace module-load captures (`R2_*`, `PLATFORM_ADMINS`, the `db` pool URL) with a getter or setter seam like `setStripeFactory`, so tests do not depend on import order or process isolation ([Fowler Injection](https://martinfowler.com/articles/injection.html), [Node test](https://nodejs.org/api/test.html)).
3. **Start each run, or each worker, from a known state** instead of relying on `after` cleanup. Clone a migrated and seeded template with `CREATE DATABASE … TEMPLATE`, with the template left unconnected ([Fowler Non-Determinism](https://martinfowler.com/articles/nonDeterminism.html), [PG CREATE DATABASE](https://www.postgresql.org/docs/current/sql-createdatabase.html)). Keep the per-test cleanup as belt-and-braces.
4. **Move slow, load-style tests out of the PR gate** into a post-merge or nightly job whose failures page someone ([SWE@Google ch23](https://abseil.io/resources/swe-book/html/ch23.html)).
5. **Define a quarantine path for flaky tests:** capped, tracked, fixed quickly. The "no skips in CI" rule currently leaves only delete-or-block ([Fowler Non-Determinism](https://martinfowler.com/articles/nonDeterminism.html)). This is a policy decision for a human (`CLAUDE.md` § Testing).
6. **Optional, lowest priority:** savepoint and pinned-connection rollback per test. It is possible with documented primitives, but it stops testing the real pool, and Better Auth's writes would also have to be routed onto the pinned connection. Prefer #3.
