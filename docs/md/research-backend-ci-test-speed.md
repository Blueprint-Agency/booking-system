# Research: why the backend CI test job takes ~9 minutes, and what the sources say to do

_Researched 2026-09-25. Question: are the claims made about the `test` job in `.github/workflows/deploy-be.yml` (Node's per-file processes, `--test-isolation`, Postgres non-durable settings, sharding, "common practice" for PR check times) correct? Only primary sources are used: Node.js docs and source, PostgreSQL docs, GitHub Docs, the Docker `postgres` image docs, Martin Fowler, DORA and the Google Testing Blog._

## 1. Summary verdict

Most of the claims hold up, with two corrections that matter. **The main one:** CI runs Node **22.23.2**, and on Node 22 the flag is only `--experimental-test-isolation`. `--test-isolation` was renamed and marked stable in **v23.6.0**, and that change never reached 22.x. `node@22 --test-isolation=none` exits with `bad option` (checked locally on v22.23.3). `docs/md/testing.md` gives the Node 23+ spelling. **The second one:** GitHub-hosted service containers now **do** accept `command:` (and `entrypoint:`). So Postgres `-c fsync=off …` can go straight on the service, and no `docker run` workaround is needed. The rest is confirmed: one child process per file by default, all files loaded before any test under `none`, top-level hooks attaching to the run-wide root, `--test-concurrency` semantics, `--test-force-exit`, the Postgres non-durable settings and their caveats, matrix limits and `fail-fast`, `--test-shard`, and the ~10-minute guidance from DORA and Fowler. The "affected tests only" practice has a first-party source (Google). "Run slow tests less often" is described by Fowler and DORA as a staged or secondary build, not as a rule.

## 3. Evidence per claim

### 1. Test isolation (`node --test`)

- **Default and `none`.** From Node's `cli.md`: "When `mode` is `'process'`, each test file is run in a separate child process. When `mode` is `'none'`, all test files run in the same process as the test runner. The default isolation mode is `'process'`." ([nodejs.org/api/cli.html](https://nodejs.org/api/cli.html#--test-isolationmode))
- **Version history.** The flag first appeared in the v22.x docs as `--experimental-test-isolation=mode`, with `added: v22.8.0` and "Stability: 1.0 - Early development" ([v22 docs](https://nodejs.org/docs/latest-v22.x/api/cli.html#--experimental-test-isolationmode)). The v23 and main docs list `--test-isolation=mode` with `added: v22.8.0` and a change entry: "v23.6.0 … This flag was renamed from `--experimental-test-isolation` to `--test-isolation`" ([PR #56298](https://github.com/nodejs/node/pull/56298)). CHANGELOG_V23 lists `test_runner,cli: mark test isolation as stable` under **Version 23.6.0 (2025-01-07)** ([changelog](https://github.com/nodejs/node/blob/main/doc/changelogs/CHANGELOG_V23.md)). CHANGELOG_V22 has no such entry, so it was not backported.
  - Checked by running it: `npx node@22` (v22.23.3) with `--test-isolation=none` gave `bad option: --test-isolation=none` and exit 9, while `--experimental-test-isolation=none` exited 0. CI uses Node **22.23.2** (`Found in cache @ /opt/hostedtoolcache/node/22.23.2/x64` in the run log). On CI's Node, the only spelling that works is `--experimental-test-isolation=none`. On Node 23.6+ (and 24+), `--test-isolation=none` works unflagged.
- **Load before run.** From the test.md "Test runner execution model" section: "When process-level test isolation is disabled, each matching test file is imported into the test runner process. Once all test files have been loaded, the top level tests are executed with a concurrency of one. Because the test files are all run within the same context, it is possible for tests to interact with each other in ways that are not possible when isolation is enabled." ([nodejs.org/api/test.html](https://nodejs.org/api/test.html#test-runner-execution-model))
- **Top-level hooks.** The docs don't say this. They only say `before()` "creates a hook that runs before executing a suite". The source does show it. In `lib/internal/test_runner/harness.js` (v22.x), `hook()` does `const parent = testResources.get(executionAsyncId()) || lazyBootstrapRoot();`. Called outside any test or suite, the parent is the global root, and under `none` there is one root for the whole process. An experiment on Node 22 confirmed it: with file `a` calling a top-level `beforeEach` and file `b` having one test, `--experimental-test-isolation=none` printed `load a`, `load b`, then `a-hook fires` **twice** (once for `a1` and once for `b1`). Under default isolation the hook fired once.

### 2. `--test-concurrency`

"The maximum number of test files that the test runner CLI will execute concurrently. If `--test-isolation` is set to `'none'`, this flag is ignored and concurrency is one. Otherwise, concurrency defaults to `os.availableParallelism() - 1`." ([cli.md](https://nodejs.org/api/cli.html#--test-concurrency); the v22 text is the same except that it names `--experimental-test-isolation`.) So under `none`, files run one at a time and `--test-concurrency=1` is redundant. Under `process`, it caps concurrent child processes, which is what the repo sets to 1.

### 3. `--test-force-exit`

"Configures the test runner to exit the process once all known tests have finished executing even if the event loop would otherwise remain active." Added in v22.0.0 and v20.14.0 ([cli.md](https://nodejs.org/api/cli.html#--test-force-exit)). This matches the workflow comment's reason for using it: open Postgres sockets after a failed `after` hook.

### 4. Postgres non-durable settings, and how to set them on a GitHub service

- **§14.5 Non-Durable Settings** ([PG 16](https://www.postgresql.org/docs/16/non-durability.html)): "Durability is a database feature that guarantees the recording of committed transactions even if the server crashes or loses power. However, durability adds significant database overhead, so if your site does not require such a guarantee, PostgreSQL can be configured to run much faster." The list includes: "Place the database cluster's data directory in a memory-backed file system (i.e., RAM disk)", "Turn off fsync; there is no need to flush data to disk.", "Turn off synchronous_commit; there might be no need to force WAL writes to disk on every commit. This setting does risk transaction loss (though not data corruption) in case of a crash of the database.", "Turn off full_page_writes; there is no need to guard against partial page writes.", "Increase max_wal_size and checkpoint_timeout", "Create unlogged tables".
- **`fsync` caveat** ([PG 16 WAL config](https://www.postgresql.org/docs/16/runtime-config-wal.html)): "it is only advisable to turn off fsync if you can easily recreate your entire database from external data. Examples of safe circumstances … using a database cluster for processing a batch of data after which the database will be thrown away and recreated". A CI database that the harness migrates and seeds on every run fits this. `fsync` and `full_page_writes` "can only be set in the postgresql.conf file or on the server command line". `synchronous_commit` "can be changed at any time".
- **Passing them to the service.** Current GitHub Docs document `jobs.<job_id>.services.<service_id>.command`: "Overrides the Docker image's default command (`CMD`). The value is passed as arguments after the image name in the `docker create` command." They also document `.entrypoint` ([workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idservicesservice_idcommand)). The section is wrapped in `{% ifversion fpt or ghec %}` in the docs source, so it applies to github.com, not GHES. The Docker image docs say "any options passed to the docker command will be passed along to the `postgres` server daemon", for example `postgres -c shared_buffers=256MB` ([docker-library/docs postgres](https://github.com/docker-library/docs/blob/master/postgres/content.md)). So this should work:
  ```yaml
  services:
    postgres:
      image: postgres:16
      command: -c fsync=off -c synchronous_commit=off -c full_page_writes=off
  ```
  - `services.<id>.options` takes "Additional Docker container resource options … see `docker create` options", and "The `--network` option is not supported." Because it accepts `docker create` options, `--tmpfs` should also work for the RAM-disk option, but no GitHub doc shows it for Postgres.
  - Two other documented routes: (a) `POSTGRES_INITDB_ARGS` passes arguments to `initdb`, and PG 16's `initdb -c name=value` "install[s] that setting in the generated postgresql.conf file, so that it will apply during future server runs" ([PG 16 initdb](https://www.postgresql.org/docs/16/app-initdb.html)). This option is not in the PG 15 docs. (b) After the service starts, run `ALTER SYSTEM SET …` and then `SELECT pg_reload_conf()`. ALTER SYSTEM writes `postgresql.auto.conf`, and values take effect "after the next server configuration reload" ([PG 16 ALTER SYSTEM](https://www.postgresql.org/docs/16/sql-altersystem.html)). A `docker run` step is no longer needed.
- **How much it saves here: not measured.** The sources say "much faster" in general. How much of this suite's time is WAL/fsync was not measured.

### 5. Sharding

- **Matrix.** "A matrix will generate a maximum of 256 jobs per workflow run. This limit applies to both GitHub-hosted and self-hosted runners." `fail-fast`: "If … set to `true` … GitHub will cancel all in-progress and queued jobs in the matrix if any job in the matrix fails. This property defaults to `true`." `max-parallel`: "By default, GitHub will maximize the number of jobs run in parallel depending on runner availability." ([workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idstrategymatrix)) Each matrix job gets its own runner, and so its own service container.
- **Node sharding.** `--test-shard`, added v20.5.0 and v18.19.0: "Test suite shard to execute in a format of `<index>/<total>` … This command will divide all tests files into `total` equal parts, and will run only those that happen to be in an `index` part." Example: `node --test --test-shard=1/3` ([cli.md](https://nodejs.org/api/cli.html#--test-shard)). It splits by **file count**, not by duration. A 66.5 s file lands in whichever shard it lands in.

### 6. Common practice

- **(a) ~10 minutes.** DORA: "The tests should not take more than a few minutes to run, with an upper limit of about 10 minutes according to DORA's research … If your build takes longer than this, you should improve the efficiency of your tests, add more compute resources so you can run them in parallel, or split out longer-running tests into a separate build using the deployment pipeline pattern." ([dora.dev](https://dora.dev/capabilities/continuous-integration/)) Fowler: "For most projects, however, the XP guideline of a ten minute build is perfectly within reason" ([martinfowler.com](https://martinfowler.com/articles/continuousIntegration.html)). Neither source is about "PR checks" specifically. Both talk about the commit or mainline build.
- **(b) Affected tests.** Google Testing Blog (Gupta, Ivey, Penix, 2011): "we built a continuous integration system that uses dependency analysis to determine all the tests a change transitively affects and then runs only those tests for every change." ([testing.googleblog.com](https://testing.googleblog.com/2011/06/testing-at-speed-and-scale-of-google.html)) This describes Google's own system at monorepo scale with a build-dependency graph. It does not recommend skipping the full suite on small repos.
- **(b) Slow tests less often.** Fowler describes a two-stage pipeline: the first stage runs "localized unit tests with slow services replaced by Test Doubles … keeping within the ten minute guideline", and the second "runs a different suite of tests that do hit a real database … Since the secondary build may be much slower, it may not run after every commit." He adds that "any later-stage failure leads to new tests in the commit build". The Google "Test Sizes" post (Simon Stewart, 2010) defines Small, Medium and Large tests by resources (Medium: "Database Yes", "localhost only" network) and time limits of 60 / 300 / 900+ seconds ([testing.googleblog.com](https://testing.googleblog.com/2010/12/test-sizes.html)). **That post says nothing about how often each size runs.** A "run large tests less often" claim cannot be cited to it.

### 7. Repo facts

- `be/package.json`: `"check": "node --import tsx --test \"src/**/*.test.ts\" \"tools/**/*.test.ts\""`. No isolation flag, so it runs one process per file.
- `.github/workflows/deploy-be.yml`, `test` job: `ubuntu-latest`, `timeout-minutes: 20`, `postgres:16` service with env, ports and health-check `options`, and no `command`. `node-version: 22`. The command is `node --import tsx --test --test-concurrency=1 --test-force-exit --experimental-test-coverage … --test-reporter=tap … "src/**/*.test.ts" "tools/**/*.test.ts"`. There is no isolation flag, so it defaults to `process`: one child process per file, one at a time.
- `be/src/test/harness.ts`: loads, migrates and seeds once **per process** and takes `pg_advisory_lock(HARNESS_RUN_LOCK)` for the life of the process. The setup comment explains that the lock is taken per run, not per file. 72 test files call `startTestApp`, which matches the 72 harness setups seen in CI. There are 140 test files in total, and 6 have a hook call at column 0 (a rough grep for top-level `before/after/beforeEach/afterEach`).
- `docs/md/testing.md` already says "`node --test` starts a process per file … That is most of CI's test time". It proposes `--test-isolation=none`, which as shown in section 1 **must be spelled `--experimental-test-isolation=none` on Node 22**.
- PR #296 ("Test harness: load the app once per process; one test database per worktree", OPEN) changes `.claude/hooks/affected-tests.mjs`, `be/.env.example`, `be/package.json`, `be/scripts/test-db.mjs`, `be/src/test/{environment,harness,harness.test}.ts`, `docs/md/test-guardrails.md` and `docs/md/testing.md`. It does **not** touch `.github/workflows/deploy-be.yml`, so CI isolation is unchanged.
- CI run 36088722010 (from the log saved locally): TAP `# tests 1295`, `# fail 14`, `# duration_ms 547362.22`.

## 4. Recommendations, as supported by the sources

1. **Get under DORA's ~10-minute ceiling first**, using DORA's own three levers in order: make the tests more efficient, run them in parallel, or split out the long-running ones ([DORA](https://dora.dev/capabilities/continuous-integration/)).
2. **Load the app once, not 72 times.** Run the suite in one process with `--experimental-test-isolation=none` on Node 22, or `--test-isolation=none` after moving to Node ≥ 23.6 (the Dockerfile has to move too, per the job's Node-parity check). First fix the files the [execution model](https://nodejs.org/api/test.html#test-runner-execution-model) breaks: top-level hooks and top-level `process.env` or import-order dependence, as `testing.md` already lists.
3. **Make the throwaway Postgres non-durable** with `command: -c fsync=off -c synchronous_commit=off -c full_page_writes=off` on the service. PG docs call this safe for a database "thrown away and recreated" ([PG WAL config](https://www.postgresql.org/docs/16/runtime-config-wal.html)). Measure the gain before and after, because no source gives a number.
4. **If still over 10 minutes, shard across a matrix** with `--test-shard=${{ matrix.shard }}/N`. Each job gets its own runner and Postgres, so the serial constraint only applies within a shard. Set `fail-fast: false` if you want every shard's failures reported, since the default `true` cancels the others. Shards split by file count, so the 66.5 s test will make one shard slower than the rest.
5. **Tiering (affected-only on PR, full suite later) is described practice, not a requirement.** Fowler requires later-stage failures to feed new tests back into the commit build. The repo's current rule, "CI runs the whole suite on every PR", is a choice those sources don't contradict.

## 5. Could not verify

- How much time `fsync=off` and the other settings save on this suite. No primary source gives a figure, and it was not measured here.
- A Node doc sentence stating that top-level hooks attach to the root under `none`. This is established only from the Node source and an experiment.
- A first-party source saying PR checks specifically, as opposed to the commit or mainline build, should be under 10 minutes.
- A first-party source saying large or slow tests should run less often by size class. The Google "Test Sizes" post defines sizes and time limits only. Fowler's secondary-build description is the nearest match.
- Whether `services.<id>.command` is available on GitHub Enterprise Server. The docs gate it to github.com and GHEC.
- Why the 14 `finance.test.ts` failures happen. They are out of scope, and they reportedly also fail on unmodified staging.
